# Технічне завдання: BookingPlatform

Платформа для пошуку та бронювання готелів. Командний проєкт курсу «Командний проєкт .NET».
Орієнтовний термін — 1 місяць (4 тижні).

## 1. Мета

Створити вебзастосунок, у якому гість знаходить готель за містом, датами та кількістю гостей,
бронює номер та керує своїми бронюваннями, а власник готелю керує номерним фондом, цінами
і підтверджує бронювання.

## 2. Ролі користувачів

| Роль | Можливості |
|------|------------|
| Гість (неавторизований) | пошук готелів, перегляд сторінки готелю та номерів, реєстрація |
| Клієнт | усе, що гість, а також бронювання, скасування, історія бронювань, відгуки |
| Власник готелю | керування своїми готелями та номерами, цінами, підтвердження і відхилення бронювань |
| Адміністратор | керування користувачами, модерація готелів і відгуків |

## 3. Функціональні вимоги

### 3.1 Облікові записи
- Реєстрація та вхід за email і паролем, пароль зберігається лише у вигляді хешу PBKDF2.
- Автентифікація токеном (JWT) для API та cookie для вебсторінок.
- Профіль користувача: ім'я, телефон, зміна пароля.

### 3.2 Каталог готелів
- Готель: назва, опис, місто, адреса, зірковість, зручності, фотографії.
- Номер: тип, місткість, ціна за ніч, площа, фотографії.
- Пошук за містом, датами заїзду та виїзду, кількістю гостей; фільтри за ціною, зірковістю, зручностями.
- Сортування за ціною та рейтингом, постраничний вивід.

### 3.3 Бронювання
- Створення бронювання на діапазон дат; виїзд має бути пізніше за заїзд.
- Номер не можна забронювати на дати, що перетинаються з активним бронюванням.
- Кількість гостей не може перевищувати місткість номера.
- Сума бронювання = кількість ночей × ціна за ніч, ціна фіксується на момент бронювання.
- Статуси: `Pending` → `Confirmed` → `Completed`; `Cancelled` доступний з `Pending` і `Confirmed`.
- Скасування безкоштовне не пізніше ніж за 48 годин до заїзду.

### 3.4 Відгуки
- Відгук можна залишити лише після завершеного бронювання, оцінка від 1 до 5.
- Рейтинг готелю — середнє арифметичне оцінок.

### 3.5 Кабінет власника
- Створення, редагування та приховування готелів і номерів.
- Календар зайнятості номерів.
- Перелік вхідних бронювань із підтвердженням або відхиленням.

### 3.6 Адміністрування
- Блокування користувачів, модерація готелів і відгуків.

## 4. Нефункціональні вимоги

- Час відповіді пошуку не більше 500 мс при 10 000 готелів.
- Усі паролі та токени зберігаються безпечно, конфігурація секретів — поза репозиторієм.
- Покриття модульними тестами доменної логіки не менше 80 %.
- Українська мова інтерфейсу, відображення коректне на екранах від 360 px.
- Журналювання помилок та запитів.

## 5. Технології

| Шар | Технологія |
|-----|-----------|
| Платформа | .NET 10, C# |
| Веб | ASP.NET Core MVC + Web API |
| Дані | Entity Framework Core, SQLite для розробки, SQL Server для розгортання |
| Автентифікація | ASP.NET Core Authentication, JWT |
| Тести | xUnit |
| Фронтенд | Razor, Bootstrap, трохи JavaScript |
| CI | GitHub Actions: збірка та запуск тестів |
| Контейнеризація | Docker |

## 6. Архітектура

Багатошарове рішення:

- `BookingPlatform.Domain` — сутності, значення-об'єкти та правила предметної області без залежностей від інфраструктури;
- `BookingPlatform.Web` — контролери, подання, REST API, налаштування DI;
- `BookingPlatform.Domain.Tests` — модульні тести доменної логіки.

На наступних етапах додаються шари `Application` (сценарії використання) та `Infrastructure` (EF Core, пошта, файли).

## 7. Модель даних

| Сутність | Ключові поля |
|----------|--------------|
| User | Id, Email, PasswordHash, Name, Phone, Role, IsBlocked |
| Hotel | Id, OwnerId, Name, Description, City, Address, Stars, IsHidden |
| Amenity | Id, Name |
| Room | Id, HotelId, Number, Type, Capacity, PricePerNight, Area |
| Reservation | Id, RoomId, GuestId, CheckIn, CheckOut, Guests, TotalPrice, Status, CreatedAt |
| Review | Id, ReservationId, HotelId, GuestId, Rating, Text, CreatedAt |
| Photo | Id, OwnerType, OwnerId, Path |

## 8. REST API (початковий перелік)

| Метод | Адреса | Призначення |
|-------|--------|-------------|
| POST | `/api/auth/register` | реєстрація |
| POST | `/api/auth/login` | вхід, видача токена |
| GET | `/api/hotels` | пошук готелів |
| GET | `/api/hotels/{id}` | сторінка готелю |
| POST | `/api/hotels` | створення готелю (власник) |
| GET | `/api/hotels/{id}/rooms` | номери готелю з доступністю на дати |
| POST | `/api/reservations` | створення бронювання |
| GET | `/api/reservations` | бронювання поточного користувача |
| POST | `/api/reservations/{id}/cancel` | скасування |
| POST | `/api/reservations/{id}/confirm` | підтвердження (власник) |
| POST | `/api/hotels/{id}/reviews` | відгук |

## 9. Розподіл задач між учасниками

Команда — 2 учасники: Петро та Костянтин.

| Учасник | Зона відповідальності |
|---------|-----------------------|
| Петро | облікові записи та безпека (реєстрація, вхід, JWT, ролі, профіль, адміністрування), каталог (готелі, номери, фото), пошук і фільтри, сторінки каталогу |
| Костянтин | структура рішення, доменна модель і правила бронювання, сценарії бронювання та скасування, кабінет власника (підтвердження бронювань), відгуки, модульні тести, CI, Docker, документація |

Інтеграція: кожен змінює код іншого лише через pull request, другий учасник виконує код-рев'ю.
Договір між шарами (інтерфейси сервісів та формат API) погоджується на першому тижні.

### 9.1 Календарний план

| Тиждень | Мета | Результат |
|---------|------|-----------|
| 1 | Основа | репозиторій, рішення, доменна модель, налаштування БД та міграцій, CI |
| 2 | Користувачі та каталог | автентифікація, ролі, CRUD готелів і номерів, перший варіант пошуку |
| 3 | Бронювання | створення і скасування бронювань, перевірка доступності, кабінет власника, відгуки |
| 4 | Стабілізація | тести, виправлення помилок, Docker, оформлення, демонстрація |

### 9.2 Розподіл за тижнями

| Тиждень | Петро | Костянтин |
|---------|-------|-----------|
| 1 | сутність `User`, хешування паролів, схема БД та початкові дані | сутності `Hotel`, `Room`, `Reservation`, правила доменного шару, CI, шаблон тестового проєкту |
| 2 | реєстрація, вхід, JWT, ролі, CRUD готелів і номерів, завантаження фото | сервіс доступності номерів, модульні тести домену |
| 3 | пошук і фільтри, сторінки каталогу, адмін-панель | API бронювань, розрахунок вартості, політика скасування, кабінет власника, відгуки |
| 4 | оптимізація пошуку, перевірка прав доступу, адаптивність інтерфейсу | злиття гілок, Docker, README, демонстрація |

### 9.3 Пріоритети

- Обов'язково: облікові записи (3.1), каталог і пошук (3.2), бронювання (3.3), кабінет власника (3.5).
- Бажано, якщо вистачить часу: відгуки (3.4), адміністрування (3.6), фотографії.

## 10. Процес роботи

- Гілка `main` захищена, зміни надходять через pull request зі схваленням іншого учасника.
- Кожна задача — окрема гілка `feature/<короткий-опис>`.
- Повідомлення комітів короткі та змістовні.
- Код оформлюється без зайвих коментарів, важливі рішення фіксуються у `docs`.

## 11. Критерії приймання

- Гість може знайти готель за містом і датами та побачити ціни.
- Клієнт може забронювати вільний номер і скасувати бронювання за правилами.
- Номер неможливо забронювати на зайняті дати.
- Власник бачить і підтверджує бронювання своїх готелів.
- Усі модульні тести проходять, збірка в CI зелена.
- Застосунок запускається однією командою `docker compose up`.

## 12. Ризики

| Ризик | Заходи |
|-------|--------|
| Конфлікти під час злиття | короткі гілки, щоденна синхронізація з `main` |
| Малий склад команди, термін 1 місяць | пріоритети в розділі 9.3, щотижневий огляд задач, відкладення необов'язкових функцій |
| Помилки в логіці дат | винесення правил у домен і покриття тестами |
| Затримка інтеграції | договір API фіксується на першому тижні |
